# 词表设计：域划分、层级与命名

> 本文所有例子用中性占位符 `<根>` / `<子域>` / `<词>`，不引用任何具体项目的词表。

## 段位语义

**根段即消费角色**，其后可选一个**子域**，最后是**词**。最多 4 段，实际形态通常 2–3 段：

| 段 | 名称 | 判据 |
|---|---|---|
| 1 | **根** | **消费角色**——哪条代码路径解析/匹配它（见下）。名字 = `[唯一化限定] + 角色名`，判据见「根名判据」 |
| 2 | **子域**（可选） | 该角色内部的**分区**（如事件角色下的 `Damage` / `Attribute`）——**不是第二个角色** |
| 3 | **词** | 具体词 |

```text
<根>.<词>              2 段：角色内不再分区
<根>.<子域>.<词>       3 段：角色内按分区铺开
```

**深度上限 4 段（MUST）。** 按上面的形态，第 4 段是留给未来变化的**余量**，不该现在就用满；用满说明根或子域没划对，而不是"再分细一点"。

> **为什么不设统一的命名空间前缀**：UE 的 tag 命名空间全局共享（引擎 + 全部插件 + 商城内容同处一棵树），前缀确实必须承担唯一性——但这份唯一性可以由**根名自己**承担。一个项目里可以同时存在**无限定根**（`Attribute`——全项目只有一个属性系统）与**限定根**（`TcsEvent`——事件按系统分根）。判据见「根名判据」。
>
> 代价要说清：这等于把"一刀切的前缀保护"换成了"**逐根的唯一性论证**"。引入第三方内容或新插件时，必须回头查根段注册表有没有撞车。

## 域判据：消费角色（核心规则）

**域的判据是"这个词会被哪条代码路径解析/匹配"，不是"它属于哪个业务系统"，也不是"它是什么种类"。**

判定一个词的域，问一句：**哪个子系统在解析它？**

| 词的用途 | 消费角色（= 根） |
|---|---|
| 被属性系统按名查属性 | 属性根 |
| 被事件总线订阅/广播 | 事件根 |
| 被流程运行期变量袋读写 | 流程变量根 |
| 被模板注册表按 id 查模板 | 流程模板根 |
| 被内容注册表按 id 查内容定义 | 内容 id 根 |
| 被验证装置消费 | **`Probe` 根** |

### 一角色一根（正交化，MUST）

**一个根只承载一个消费角色。** 同一机制下的不同角色**各自成根**，MUST NOT 用 facet 段把两个角色兼收在一个根里：

| 反例（一根兼两角色） | 正例（各自成根） |
|---|---|
| `<机制>.Key.<词>` 与 `<机制>.Template.<词>` | `<机制>Key.<词>` 与 `<机制>Template.<词>` |

判据：`Key` 那一侧的消费者是"**运行期读写值槽**"，`Template` 那一侧的消费者是"**装配期按 id 查模板**"——两条不同代码路径 = 两个角色 = 两个根，哪怕它们同属一个机制。

**收益不止省段位**：拆根后每个根各自拿到完整深度预算，两个角色可以独立演进（一方加分区不影响另一方）。

### 根名判据（MUST）

**根名 = `[唯一化限定] + 角色名`，且必须唯一指向一个消费场景；不唯一就加限定词。**

| 名字 | 是否唯一指向一个场景 | 结论 |
|---|---|---|
| `Attribute` | 全项目只有一个属性系统 | 可不加限定 |
| `Param` / `Run` / `Chain` | 泛指，且易与别的机制撞义（`Run` 常指"单局"或"运行态"） | **必须加限定** |
| `<系统>Event` | 系统限定 + facet，指向唯一 | OK |
| `<机制>Key` / `<机制>Template` | 机制限定 + 角色，指向唯一 | OK |

#### 一个角色可以有多个解析方（MUST）

"一角色一根"说的是 **根数 = 角色数**，不是"根数 = 解析方数"。同一批词被**多个模块的代码路径**解析时，它们仍是**一个**角色、**一个**根——因为"一个 tag 文本，一处声明"不允许同一批词拆进两个根。

此时**"唯一化限定" MUST 取描述性限定（这批词描述什么），MUST NOT 取其中任一解析方的机制名**——否则名字会把其余解析方写成不存在，读者会据此在错误的根下找词。

| 反例 | 问题 | 正例 |
|---|---|---|
| `<机制A>Classification` | 词表同时被机制 A 与机制 B 匹配，名字只提 A | `<描述性限定>Classification`（说明这批词描述什么） |

**两个已实证的实例**（同一类问题的两种处置）：

| 根 | 限定词取自 | 语义实际跨 | 处置 |
|---|---|---|---|
| `<模块名>Param` | 模块名 | 该模块运行态 **+** 另一模块的运行态 | 名字不改，**注册表注明取广义**（例：`TcsStateParam` 的 "State" 含技能激活运行态，不是 `TcsState` 模块） |
| `<机制名>Classification` | 机制名 | 机制 A 的匹配面 **+** 机制 B 的匹配面 | **改描述性限定**，或同样加注记 |

**判据**：定根名之前先问一句——**"这批词只被一条代码路径解析吗？"** 答案是否时，限定词就不能取机制名。

### 根段注册表（MUST）

项目侧 MUST 维护一份**根 → 消费角色 → 声明方**的登记表；新建根之前先查表，避免两处各建一个语义重叠的根。

校验脚本的命名空间检查据此从"单一前缀"改为"**根清单白名单**"（`-Namespace` 只适用于单根项目）。

### 为什么不用"业务系统"分域

按业务系统分（`Combat.*` / `Inventory.*` / `UI.*`）看似直观，但跨系统共用的词无处安放——"属性名"同时被战斗与装备消费，按业务系统就没有正确归属。而按消费角色划分时，一个消费者只属于一侧，**域所有权天然清晰**。

### 为什么不用"词的性质"分域

"标识 / 键 / 事件"这类性质分类边界模糊：一个"参数键"和一个"流程变量键"凭性质分不开，凭消费者能分开（前者若被别的子系统解析就是另一个域；若同被流程变量袋解析就**是同一个域**——此时应合并，不要留两个域）。

**根增删判据**：新增根的**唯一理由**是出现了新的消费角色。根数量应约等于消费角色数量，**不随内容增长**。若某个根的词在无限膨胀，说明它是"内容根"而非"角色根"，错划了。

## 段命名风格

**每段 PascalCase，禁下划线，禁非 ASCII（MUST）。**

允许：`<根>.MaxHealth`、`<根>.<子域>.BaseDamage`
禁止：`<根>.Max_Health`、`<根>.maxhealth`

### 为什么禁下划线（不是审美）

C++ 常量名与 tag 文本的对应规则是"**点 → 下划线，逐段对应**"（见 [authoring.md](authoring.md)）。段内再出现下划线，这个映射就**产生反推歧义**：

```text
tag 文本:  <根>.<机制名>Template.Default_Slice
常量名:    Tag_<根>_<机制名>Template_Default_Slice
                                        └─ Default_Slice 是一段还是两段？无法反推
```

读代码的人据此反推出错误的层级，是**已实际发生过的踩坑现场**。引擎自身的先例也是逐段对应：`Mover.IsOnGround` ↔ `Mover_IsOnGround`。

### 字符约束以引擎为准

引擎的 `InvalidTagCharacters` 默认值是 `"` `'` `,`（`GT/Private/GameplayTagsSettings.cpp:70`，管理器另追加 `\r\n\t`，`GT/Private/GameplayTagsManager.cpp:617`）。**点与下划线引擎并不禁止**——禁下划线是本规范的约定，不是引擎限制。ASCII 之外的字符同理：引擎多半放行，但会破坏可读性与跨工具一致性，故本规范禁止。

## 正交维度禁入路径

**生命周期（临时/验证中/废弃）、优先级、状态、开发阶段等与"词义"无关的维度，一律不得作为层级段（MUST）。**

反例形态：

```text
<根>.Temp.<子域>.<词>        ← Temp 是生命周期，不是词义
<根>.WIP.<词>                ← 同上
<根>.Deprecated.<词>         ← 同上
```

这类维度只允许两种表达方式：

1. **独立根**（仅 `Probe`，见下）——合法性来自"它是消费角色"，不来自"它是临时的"
2. **`DevComment` 标注**——用于正式词的状态说明，不进路径

## 临时验证词：`Probe` 根

临时/验证用的词一律落独立根（MUST）：

```text
Probe.<机制名>.<词>        3 段：该机制的一条验证词
Probe.<机制名>             2 段：装置本体
```

**关键约束：机制名压成一段，不要把原路径原样搬进 `Probe`。** 两条理由：

1. **留深度余量**——`Probe` 自己占一段，若原路径照搬就是 4 段撑满上限，以后无处可加：

   ```text
   <机制>Key.<子域>.<装置>.<词>      4 段（原文，合法）
   <机制>Key.Temp.<子域>.<词>        4 段（Temp 是生命周期维度，违规）
   Probe.<机制>Key.<子域>.<词>       4 段（合法但撑满，零余量）
   Probe.<机制>.<词>                 3 段 ✓
   ```

2. **断开与原路径的镜像耦合**——原路径整段照搬会让树里出现两条几乎同形的路径；正式词一旦改名/迁根，Probe 词不会跟着动，于是**静默分叉**。压成一段后两者各自独立，退役时整子域删掉即可。

**代价与检查面**：扁平化会把原本靠路径区分的东西挤到同一个命名空间里，**同名冲突会浮现**（同一装置内的同名、跨装置的同名）。落位时逐条检查：`<词>` 在**同一机制子域内**唯一，且**跨机制不撞名**。这是落位时的实际工作量，不能省。

### 边界声明（必须写清，否则规则自相矛盾）

`Probe` **不是**"生命周期维度进了路径"的例外——它的合法性来自**消费角色**（验证装置是消费者），和"属性系统消费属性 tag"是同一类事实。一条正式词与一条 Probe 词的区别是**消费者不同**，不是"临时的 vs 正式的"。

因此：**不要**把"临时"当成分根理由，而要把"哪个装置消费它"当成分根理由。

### 退役

验证收束时**整根删除**（MUST）——按机制逐个删子域，最终删掉 `Probe` 根本身。删除动作见 [authoring.md](authoring.md)「改名与重定向」与 [engine-facts.md](engine-facts.md)「悬空引用捕获」。

> **判据先行**：落位一个 Probe 词时就在 `DevComment` 里写清"验证什么、由哪个提案引入、验证完删什么"。没有退役判据的验证词不允许进词表——否则它会永久留在那里（已有项目出现过"16 条里 16 条都标着'验证后可删'却从未被清理"的状态）。

## 词表审查速查

- 段数 ≤ 4（且第 4 段是余量，不是现状）？
- **根段能用"哪个子系统解析它"回答出来吗？**
- **一个根只承载一个角色吗？（同一机制的两个角色有没有被塞进一个根）**
- **根名唯一指向一个消费场景吗？不唯一加限定词了吗？**
- **新建根前查过根段注册表吗？**
- 每段都是 PascalCase、无下划线、纯 ASCII？
- 路径里没有任何生命周期/优先级/状态段？
- 临时词在 `Probe` 根下、机制名压成一段、且 `DevComment` 有退役判据？
