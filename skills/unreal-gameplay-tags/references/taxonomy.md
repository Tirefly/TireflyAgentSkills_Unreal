# 词表设计：域划分、层级与命名

> 本文所有例子用中性占位符 `<Ns>`（命名空间）与 `<域>` / `<词>`，不引用任何具体项目的词表。

## 段位语义

一个 tag 的段位含义是固定的，最多 4 段：

| 段 | 名称 | 判据 |
|---|---|---|
| 1 | **命名空间** | 框架/项目根前缀，如 `<Ns>`。UE 的 tag 命名空间是**全局共享**的（引擎 + 全部插件 + 商城内容同处一棵树），故前缀必填 |
| 2 | **域** | **消费角色**——哪条代码路径解析/匹配它（见下） |
| 3 | **子域**（可选） | 该角色内部的**词形态**（如 `Key` / `Template` / `Damage`） |
| 4 | **词** | 具体词 |

```text
<Ns>.<域>.<词>             3 段：域内不分形态时
<Ns>.<域>.<子域>.<词>      4 段：域内有多种词形态时
```

**深度上限 4 段（MUST）。** 超过 4 段说明域或子域没划对，而不是"再分细一点"。

## 域判据：消费角色（核心规则）

**域的判据是"这个词会被哪条代码路径解析/匹配"，不是"它属于哪个业务系统"，也不是"它是什么种类"。**

判定一个词的域，问一句：**哪个子系统在解析它？**

| 词的用途 | 消费角色（= 域） |
|---|---|
| 被属性系统按名查属性 | 属性域 |
| 被事件总线订阅/广播 | 事件域 |
| 被流程运行期变量袋读写 | 流程域的 `Key` 子域 |
| 被模板注册表按 id 查模板 | 流程域的 `Template` 子域 |
| 被内容注册表按 id 查内容定义 | 内容 id 域 |
| 被验证装置消费 | **`Probe` 域** |

### 为什么不用"业务系统"分域

按业务系统分（`Combat.*` / `Inventory.*` / `UI.*`）看似直观，但跨系统共用的词无处安放——"属性名"同时被战斗与装备消费，按业务系统就没有正确归属。而按消费角色划分时，一个消费者只属于一侧，**域所有权天然清晰**。

### 为什么不用"词的性质"分域

"标识 / 键 / 事件"这类性质分类边界模糊：一个"参数键"和一个"流程变量键"凭性质分不开，凭消费者能分开（前者若被别的子系统解析就是另一个域；若同被流程变量袋解析就**是同一个域**——此时应合并，不要留两个域）。

**域增删判据**：新增顶层域的**唯一理由**是出现了新的消费角色。域数量应约等于消费角色数量，**不随内容增长**。若某个域的词在无限膨胀，说明它是"内容域"而非"角色域"，错划了。

## 段命名风格

**每段 PascalCase，禁下划线，禁非 ASCII（MUST）。**

允许：`<Ns>.<域>.MaxHealth`、`<Ns>.<域>.<子域>.BaseDamage`
禁止：`<Ns>.<域>.Max_Health`、`<Ns>.<域>.maxhealth`

### 为什么禁下划线（不是审美）

C++ 常量名与 tag 文本的对应规则是"**点 → 下划线，逐段对应**"（见 [authoring.md](authoring.md)）。段内再出现下划线，这个映射就**产生反推歧义**：

```text
tag 文本:  <Ns>.<域>.<子域>.Default_Slice
常量名:    Tag_<Ns>_<域>_<子域>_Default_Slice
                                    └─ Default_Slice 是一段还是两段？无法反推
```

读代码的人据此反推出错误的层级，是**已实际发生过的踩坑现场**。引擎自身的先例也是逐段对应：`Mover.IsOnGround` ↔ `Mover_IsOnGround`。

### 字符约束以引擎为准

引擎的 `InvalidTagCharacters` 默认值是 `"` `'` `,`（`GT/Private/GameplayTagsSettings.cpp:70`，管理器另追加 `\r\n\t`，`GT/Private/GameplayTagsManager.cpp:617`）。**点与下划线引擎并不禁止**——禁下划线是本规范的约定，不是引擎限制。ASCII 之外的字符同理：引擎多半放行，但会破坏可读性与跨工具一致性，故本规范禁止。

## 正交维度禁入路径

**生命周期（临时/验证中/废弃）、优先级、状态、开发阶段等与"词义"无关的维度，一律不得作为层级段（MUST）。**

反例形态：

```text
<Ns>.<域>.Temp.<子域>.<词>        ← Temp 是生命周期，不是词义
<Ns>.<域>.WIP.<词>                ← 同上
<Ns>.<域>.Deprecated.<词>         ← 同上
```

这类维度只允许两种表达方式：

1. **独立顶层域**（仅 `Probe`，见下）——合法性来自"它是消费角色"，不来自"它是临时的"
2. **`DevComment` 标注**——用于正式词的状态说明，不进路径

## 临时验证词：`Probe` 域

临时/验证用的词一律落独立顶层域（MUST）：

```text
<Ns>.Probe.<装置标识>.<词>        4 段上限内
<Ns>.Probe.<装置标识>             装置本体，3 段
```

**关键约束：原所属域不作段。** 这是被 4 段上限逼出来的——把一个 5 段的深层词"搬进 Probe 域"若不砍掉原域，只会换个位置继续 5 段：

```text
<Ns>.<域>.<子域>.Temp.<装置>.<词>     6 段（违规）
<Ns>.Probe.<域>.<子域>.<装置>.<词>    仍是 5 段（换个位置的违规）
<Ns>.Probe.<装置>.<词>                4 段 ✓
```

**代价与检查面**：扁平化会把原本靠路径区分的东西挤到同一个命名空间里，**同名冲突会浮现**。落位时逐条检查：`<词>` 在**同一装置内**唯一，且**跨装置不撞名**。这是落位时的实际工作量，不能省。

### 边界声明（必须写清，否则规则自相矛盾）

`Probe` 域**不是**"生命周期维度进了路径"的例外——它的合法性来自**消费角色**（验证装置是消费者），和"属性系统消费属性 tag"是同一类事实。一条正式词与一条 Probe 词的区别是**消费者不同**，不是"临时的 vs 正式的"。

因此：**不要**把"临时"当成分域理由，而要把"哪个装置消费它"当成分域理由。

### 退役

验证收束时**整域删除**（MUST）——按装置逐个删子域，最终删掉 `Probe` 域本身。删除动作见 [authoring.md](authoring.md)「改名与重定向」与 [engine-facts.md](engine-facts.md)「悬空引用捕获」。

> **判据先行**：落位一个 Probe 词时就在 `DevComment` 里写清"验证什么、由哪个提案引入、验证完删什么"。没有退役判据的验证词不允许进词表——否则它会永久留在那里（已有项目出现过"16 条里 16 条都标着'验证后可删'却从未被清理"的状态）。

## 词表审查速查

- 段数 ≤ 4？
- 段 2 能用"哪个子系统解析它"回答出来？
- 每段都是 PascalCase、无下划线、纯 ASCII？
- 路径里没有任何生命周期/优先级/状态段？
- 临时词在 `Probe` 域、且 `DevComment` 有退役判据？
- 新增顶层域了吗？如果是，理由是不是"出现了新的消费角色"？
